Open source

Teach one idea in 3D. Leave it where everyone can use it.

Kodolab is a growing library of interactive biology: real molecules, real structures, built in the open. The pages are plain HTML and Three.js with no build step, so a coding agent can add to it in an afternoon. What an agent cannot decide is whether the science is right, or whether a student would actually learn something. That is the part we do together.

Find your way in ↓ Read the repo AGPL-3.0 · no build step · no account

Agents made this cheap

Building a molecule in 3D used to mean learning Three.js first. Now you describe the thing you want to teach and your agent drafts it from the docs already in this repo. The work that took a weekend takes an evening.

Review is the scarce part

Today's coding agents write good graphics and plausible biology. Plausible is the problem. A wrong bond angle, a membrane the wrong way round, a tidy story that skips the mechanism: all of it renders beautifully. Every contribution gets read by a person who knows the subject.

One library compounds

Fifty people generating on their own gives fifty half-finished cells that nobody else can reach. Add to one library and the next person's lesson mounts your cell by name, at the right scale, in the same chrome, next to a protein someone else baked.

Ways in

Four sizes of contribution, smallest first

Pick one and read only the doc it names. The repo has a routing table for exactly this reason: reading everything before you start is how the important rule gets lost among forty that did not apply.

  • 01 · No code20 minutes

    Review the science and the teaching

    Open a lesson and find the thing that is wrong, oversimplified, or badly explained. Say what a student would walk away believing, and what they should have. This is the contribution the project needs most, and it needs no setup at all.

    Read
    The lesson itself. Start at kodolab.org
    Done when
    An issue names the claim, where it appears, and what it should say instead
  • 02 · Smallan evening

    Add a molecule or a protein

    A molecule is a spec in a lib/mol-*.js file: atoms in real ångströms, bonds, names. A protein is baked from its Protein Data Bank entry into the coordinates a page loads. The narrowest way in, and the checkers do a lot of the reviewing for you.

    Read
    AddingAMolecule.md or AddingAProtein.md
    Done when
    node check-molecules.js passes and it looks right in molecule-viewer.html
  • 03 · Mediuma weekend

    Build a component

    A component is a 3D scene any page can mount by name and drive by parameters: an organelle, a tissue, an organism, a process. This is the highest-leverage thing you can add. Once it is in the library, every lesson and every student-generated app can use it without writing graphics code.

    Read
    AddingAComponent.md, then Components.md
    Done when
    tools/gen-app.js writes a working page that mounts it, from the reference alone
  • 04 · Largea project

    Build a lesson

    A step-through that carries one idea from first look to understood: a scene, a handful of steps, and copy in a tutor's voice. The biggest ask, and the one that gets the most editing back from us, because the teaching is the hard part and it is worth getting right.

    Read
    AddingAPage.md and Design.md
    Done when
    It teaches one idea, the science holds up, and it runs in Safari and Chrome
Set up

Running locally takes one command

The pages have no dependencies and no build step. They load Three.js from a CDN and run straight from the working tree, which is also exactly what deploys.

  1. Fork, then clone your fork

    git clone https://github.com/YOUR-USERNAME/ScienceSandbox.git
cd ScienceSandbox

  2. Start the dev server

    Node is the only requirement, and the server itself has zero dependencies. Open http://localhost:8817/. Saving a file reloads only the pages that use it, and a CSS change swaps the stylesheet in place, so the scene keeps its camera and selection while you tune it.

    node demos/tools/dev-server.js

  3. Optional: install the checkers

    Only needed if you are touching molecules. This points git at .githooks, so the offline checkers run before each commit, and installs RDKit for the handedness check. The pages still need nothing.

    cd demos && npm i
node check-molecules.js        # geometry, bond angles, stereo claims
node tools/check-pages.js      # every page still loads what it needs

  4. Point your agent at the routing table

    demos/CLAUDE.md opens with a table that maps what you are building to the one doc you should read. Send your agent there first. A repo-wide scan costs a lot of context and still misses the rule that matters, because most of the load-bearing reasoning in this project lives in the file headers, next to the trap it is warning about.

Starter prompt

Hand this to your agent

Claude Code, Cursor, Codex, whichever you use. Replace the one line that says what you want, and let it read the repo from there.

Read demos/CLAUDE.md, then the one doc its "What to read" table names for
this task. Follow that doc exactly, including the parts that look like they
do not apply.

TASK: <one sentence: the thing you want to add, and what it should teach>

Constraints, from the repo:
  - Three.js r128 as a global script. No build, no bundler, no ES modules,
    no npm package on a page.
  - Never type an atom or bond colour. palette.js publishes them as tokens.
  - Molecule coordinates are real angstroms, not display units.
  - A claim about chemistry ships with the assertion that checks it, in the
    same commit.
  - Write like a tutor for a first-year biology student. One claim per
    paragraph, and the picture is showing it right now.

Run the checkers, then tell me exactly what to click in the browser to see
whether it is right. Do not tell me it works. I will look.

The last two lines matter more than they look. Nothing in this repo can verify framing, timing, or whether an animation reads as the thing it claims to show, so a human opens the page every time. Ask your agent for the click, not for a verdict.

Review

Open a pull request, and expect a real read

Branch off main and open a PR. In the description, say what a student should learn from it, what you checked, and what you are unsure about. That last one is the most useful sentence in the whole PR.

Expect edits on the copy. The voice is a house style and getting it consistent is part of what makes the lessons feel like one thing. Expect questions on the science. Slow is fine here. Confidently wrong and beautifully rendered is the failure this project is organised against.

Open an issue first →

What gets checked

  1. Is the science right? Geometry, mechanism, and the things a simplification quietly implies.
  2. Would a student learn it? One idea, carried. A scene that shows everything teaches nothing.
  3. Does it run? Opened in Safari and Chrome, on a laptop-sized window.
  4. Does it hold the invariants? No build step, r128, tokens for colour, ångströms for coordinates.
  5. Do the checkers pass? The pre-commit hook runs them, so this usually answers itself.

The code

AGPL-3.0. Anything built on this stays open, including a hosted copy. Kodolab only ever runs in a browser, so plain GPL would let someone serve a modified version and never publish the changes. A classroom should be able to take a lesson apart, and the next classroom should get that back.

The words and pictures

CC BY-NC 4.0. Lesson copy, images and rendered stills. Teach with them, remix them for your class, put them on your department's site, with credit. Selling them or bundling them into a paid product is a conversation, so ask. Where the line falls inside one file is in LICENSING.md.

Credit

Structures come from the Protein Data Bank and stay credited to the labs that deposited them. Contributors are credited in the commit history and on the lesson they built. No CLA, no copyright assignment: opening a PR licenses it under both, and you keep your copyright.
